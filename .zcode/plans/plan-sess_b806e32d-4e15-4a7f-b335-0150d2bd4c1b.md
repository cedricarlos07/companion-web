# COMPANION — Mem0 (mémoire principale) + Mastra (agentique principale)

Architecture cible : **Companion = produit** (Knowledge Risk, Role Brain, Handover, permissions, audit, UX) → **Mem0 = memory runtime** / **Mastra = agent runtime** → **Policy + Audit** → PostgreSQL. Les concepts métier restent Companion ; le générique part en OSS. Branche actuelle : `feat/mem0-memory-provider` (baseline commitée). Frontend gelé (branchement données uniquement), `test:demo` 18/18 = garde-fou permanent.

## Sous-phase A — Mem0 moteur mémoire

1. **Config** (env) : `MEMORY_SEARCH_ENGINE=hybrid|native|mem0` (défaut hybrid), `MEM0_VECTOR_STORE=memory|pgvector` (dev: memory, prod: pgvector), `MEM0_LLM_PROVIDER=ollama`, `MEM0_LLM_MODEL`, `MEM0_EMBEDDER_MODEL=nomic-embed-text`, `MEM0_PG_DSN` (prod). Models épinglés aussi dans la table `settings` (clé `ai`) — plus de surprise de modèles : startup health check, état degraded loggé si modèle absent, warning si `NODE_ENV=production` + PGlite.
2. **Abstraction** `server/memory/` : `memory-provider.ts` (interface add/search/get/update/history/delete/health), `companion-native.ts` (encapsule le moteur actuel), `mem0-provider.ts` (mem0ai@3.1.8 : Ollama LLM+embedder, store memory/pgvector, `customInstructions` avec nos règles métier), `index.ts` (singleton + `reindexMemoriesFromDb()` qui pousse les mémoires actives/vérifiées vers Mem0 au démarrage quand le store est vide). `buildMem0Metadata()` : organization_id, companionMemoryId, employee_id, role_id, department_id, scope, type, status, confidence, source. Toute recherche Mem0 filtre AU MINIMUM par organization_id ; le contrôle d'accès est REFait par Companion après hydratation (Mem0 jamais autoritaire).
3. **Intégration métier** : sync `mem0.add()` à la validation/promotion/réponse d'entretien (+ update/delete sur dépréciation) — best-effort loggé, la table `memories` reste le business record (BI Risk/Role Brain/provenance/versions inchangées). Pipeline Ask hybride : mem0.search → companionMemoryId → hydratation SQL → permission check (scopes initieur/agent) → ranking Companion → réponse citée ; abstention inchangée ; `native` conservé derrière le flag. L'outil agent `search_memory` utilisera le même chemin.
4. **Health + Settings** : `GET /api/system/memory-provider/health` (provider, status, latency, vectorStore, llm, embedder, lastError) ; affichage dans Settings (frontend léger).
5. **`npm run test:memory-providers`** : les 4 questions du scénario × native/mem0/hybrid → precision@5, source correctness, latence, tokens, faux positifs.
6. **Régression** : `test:demo` 18/18 + typechecks. **Checkpoint : rapport Mem0** (version, APIs réelles utilisées, bench, recommandation KEEP/PARTIAL/REJECT — si Mem0 casse le métier, le flag native redevient défaut et Mem0 reste expérimental).

## Sous-phase B — Mastra moteur agentique

1. **Sécurité d'abord** : versions **exactes épinglées** (@mastra/core, @mastra/libsql), contrôle `npm ls easy-day-js` vide + aucun `easy-day-js` dans package-lock, audit des postinstall (incident typosquat du 17/06/2026 — vol d'env vars).
2. **Tables** : migration 0002 déjà écrite sur la branche (agents, agent_runs, agent_run_steps, tool_calls, approvals, triggers, agent_feedback, settings).
3. **Structure `server/mastra/`** : `index.ts` (instance Mastra : storage LibSQL fichier en dev / @mastra/pg en prod, 4 agents, workflows), `tools.ts` (12 createTool : search_memory, get_company/employee/role/project_context, get_knowledge_gaps, create_memory_candidate, correct_memory, create_handover, create_onboarding, create_task, request_approval — chacune appelle les services Companion existants, **jamais de SQL direct**), `policy.ts` (`authorizeToolCall` : organisation, identité agent, initiateur, memory scopes, permission tool, autonomie, budgets, rate limit → `PolicyDeniedError` + audit `policy.denied`), workflows : `handover-employee` (analyse → gaps → questions → **SUSPEND** (attente réponses) → resume → candidates → SUSPEND validation → resume → pack → verify), `sales-followup` (contexte → draft → grounding eval → approval → SUSPEND → approve → **send_email MOCK** → verify), `resolve-contradiction`, `onboard-employee`, `capture-knowledge`. Agents : Knowledge (assistant), Handover (copilot), Onboarding (copilot), Company Assistant (copilot) — modèle BYOK Ollama via endpoint openai-compatible.
4. **Persistance & coûts** : chaque workflow run est lié à `agent_runs` (status queued→planning→running→waiting_approval→verifying→completed/failed/cancelled, plan, memories/sources used, prompt/completion tokens via les réponses Ollama, estimatedCost, latence, verifier score) + `agent_run_steps` (timeline synthétique, pas de chaîne de pensée) + `tool_calls` (décision policy incluse). Budgets maxRunTokens/maxDailyTokens par agent + kill switch (setting `agents.enabled` + env).
5. **Triggers** : `dispatchEvent(employee.leaving|employee.created|memory.contradicted|knowledge_risk.high|source.ingested)` appelé depuis les routes existantes → `createRunAsync` Mastra, avec rate limit par trigger.
6. **Approvals réelles** : approbation → `resume()` du workflow ; rejet → terminaison propre avec état rejeté. Page `/approvals` branchée sur l'API.
7. **Feedback** : `POST /api/runs/:id/feedback` (approve/correct/reject/rate) → `agent_feedback` ; une correction métier crée une Memory Candidate. Jamais de fine-tuning auto ni d'écrasement silencieux.
8. **Evals** : groundingEvaluator (provenance/citations), permissionEvaluator (aucune ressource interdite), goalCompletionEvaluator, executionEvaluator → score 0..1 persisté ; retries max 2, uniquement erreurs transitoires (jamais sur policy/approval/budget).
9. **UI branchée** : `/agents` (vraies cartes), `/agents/:id` (goal, status, autonomy, memory access, skills, tools, runs récents, coût, erreurs + timeline du run), `/approvals`, `/activity` (API audit existante), `/automations` (triggers réels) — fallback mock conservé.
10. **Tests** : `npm run test:agents` (A : contradiction → Knowledge Agent → review → nouvelle version ; B : « Prépare une relance pour Orange CI » → Role Brain + contexte Orange → citations → draft → approval → SUSPEND → approve → mock send → verify ; C : leaving → trigger → Handover workflow → gaps → questions → SUSPEND) et `npm run test:agent-security` (Sales→HR = DENIED, assistant→send_email = DENIED, copilot sans approval = WAITING_APPROVAL, outil inconnu = DENIED, budget dépassé = DENIED, cross-org = DENIED, modification de ses permissions = DENIED).
11. **Non-régression finale** : `test:demo` 18/18, typechecks, `npm run build`, vérification des 27 routes. **STOP + rapport** (versions, architecture, tables, APIs, workflows, tools, tests, résultats, limitations) — pas de MCP ni connecteurs dans cette phase.

## Points de vigilance connus
- Ollama local a deux magasins de modèles sur cette machine : diagnostiquer (OLLAMA_HOST/OLLAMA_MODELS) et s'assurer que l'instance qui sert :11434 a `nomic-embed-text` + un modèle de chat ; sinon état degraded documenté, fallback local assumé.
- PGlite = dev/test uniquement ; warning au démarrage si NODE_ENV=production avec PGlite.
- Le fallback heuristique ne produit jamais que des `candidate` (déjà garanties dans createMemory, conservé).
- Permissions propagées au retrieval : scopes agents/utilisateurs appliqués dans les filtres Mem0 ET re-vérifiés après hydratation SQL.
